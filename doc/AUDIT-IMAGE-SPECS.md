# 配图数值核查：手机形态 84 条

> 与 `doc/UX-SPEC-FROM-IMAGES.md` 配套。那份回答「图里读出什么」，这份回答
> 「读出来的东西对不对」—— 逐条对令牌表、正文、实现三处。
> 穿戴形态 149 条按当前范围不核，原文仍在 `doc/ux-specs/<slug>.md` 里。

## 一句话结论

84 条里 **19 条**能在「配图 / 正文 / 令牌 / 实现」四处落齐，
**45 条**是设计稿或正文有、令牌表里根本没有这一项，
**8 条**是真冲突（图与正文不一致，或两张图互相不一致），
另有 **4 条**图上读数本身就不可靠、**7 条**根本不是规格（计数或演示几何）、
**1 条**令牌有值但形态不存在（滚动文本渐隐，明确不做）。

| 结论 | 含义 | 条数 |
| --- | --- | --- |
| **A 三方一致** | 图上值 = 正文/文档原文 = 实现常量 | 19 |
| **B 令牌有、实现未引用** | 令牌值对得上，代码里没有对应形为 | 1 |
| **C 仅设计稿/正文** | 令牌表无此项，值只能靠图或正文；实现有则对、无则缺 | 45 |
| **D 冲突** | 图与正文不一致，或同一尺寸两张图给出两个值 | 8 |
| **E 读数不可靠** | 标注被裁断/字形歧义，不能当数值用 | 4 |
| **F 非规格** | 页签计数、某一台具体屏幕的演示几何 | 7 |
| **合计** | | **84** |

值得先说一句：**「令牌表里没有」占了 45 条，是压倒性多数**。这不是核查失败，
而是这类规格的真实分布 —— 设计规范写的布局规则（半模态顶距 8vp、按钮最大宽
448vp、列表侧滑图标热区）大多没有下沉成 `sys.float.*` 令牌。所以本库对这类值
直接写在常量里并注明「官方设计规范」是对的，**不需要、也找不到令牌可引**。

## 判据

三条硬规矩，本轮各撞了一次：

1. **「令牌表没有」≠「没有规格」**。设计文档正文与配图都是规格的一手来源，
   只是层级不同。判「无令牌」时必须同时说明正文有没有。
2. **「值相同」≠「同一个令牌」**。按钮最大宽 `448vp` 与资源表里的
   `account_button_max_size = 448vp` 数值相同，但后者是账号按钮，语义不同 ——
   不能拿它当按钮 `maxWidth` 的依据。同理 `sheet_height_percent_max = 0.9`
   是半模态的，弹框的 0.9 来自弹框文档原文。
3. **「代码里有这个常量」≠「它进了布局」**。本库不是 ArkTS，不存在
   `GetAttr` 读进字段却零调用方那种形态；这里的等价陷阱是「常量定义了、
   但布局路径上没人读它」。所以每条都追到实际渲染分支。

结论类别只看**证据链是否闭合**，不看数值大小是否合理。

## 跨控件的结构性发现

### 发现 1：8vp 半模态顶距四处出现，一次都没进代码 —— **本轮已修**

`bindsheet_16`、`button_39`、`segmentbutton_10` 三张图上的「8」和
`bindsheet` 正文「Large：屏幕/窗口高度 − 信号栏 − 8」是同一个规则：
**半模态面板顶边与状态栏下缘留 8vp**。四处都指向它，令牌表里没有对应项
（`sheet_title_area_margin = -8vp` 是负值，是标题区自身的负边距，不是它）。

而实现的 `OhosSheetSize.large => viewportHeight` 与
`bottom` 分支的 `height.clamp(0.0, viewportHeight)` 都让面板顶到窗口顶。
代码注释里甚至写了「`BOTTOM` 的高度上限是「距状态栏 8vp」这类位置约束」——
**知道这条规则，但没往上限里减**。这是本轮唯一一处「规格明确、实现可改」的缺口。

修法是三步，**第二步是正文之外的一条独立事实**：

1. `OhosSheetSpec.topGap = 8`（带四处处方，注明令牌表无此项）；
2. 新增 `OhosSheetSpec.maxPanelHeight(...)`：`SIDE` / `CONTENT_COVER` 返回窗口高，
   其余三型返回 `窗口高 − 状态栏 − 8`。**状态栏必须用 `View.of(context).padding.top`
   取，不能用 `MediaQuery.paddingOf`** —— 调用点常在 `OhosScaffold` 的 `SafeArea`
   里，那里 `paddingOf` 恒为 0，量出来等于白改；
3. `LARGE` 挡、`BOTTOM` 的显式高度、`CENTER`/`POPUP` 的 90% 上限都走这一条上限
   （CENTER 的两条上限取**小**：竖屏恒是 90% 更小，横屏矮窗口才轮到 8vp 那条）。

补了 5 条用例，其中一条真的量位置（`panel.top == 状态栏 + 8`、`height == 窗口高 − 32`）。

### 发现 2：448 与 480 不是冲突，是同一个式子的两端

`480 − 2×16 = 448`。`button` 与 `segmentbutton` 的正文都用同一句话表达
「窗口化场景容器宽 − 两侧 16vp，且 ≤ 448」。两处实现都把 448 写成上限，
是对的。上一轮把它记成「图与正文差 32，可能图量的是内容宽」，方向猜对了。

### 发现 3：悬浮页签栏，设计稿与正文用的是两套公式，每页签差 4vp

| 页签数 | 断点 | 图 | `80n+8` | 正文公式 | `76n+8`/`80n+8` |
| --- | --- | --- | --- | --- | --- |
| 2 | <600 | **168** | 168 ✓ | `76×2+8` | 160 |
| 3 | <600 | **248** | 248 ✓ | `76×3+8` | 236 |
| 2 | ≥600 | **184** | `88×2+8` = 184 ✓ | `80×2+8` | 168 |
| 3 | ≥600 | **272** | `88×3+8` = 272 ✓ | `80×3+8` | 248 |

四张图的值**全部能被 `80n+8`（<600）/ `88n+8`（≥600）精确复现**，一个不差。
也就是说这不是我读错，而是设计稿确实按 80/88 排的，而 `hds-hdstabs.md` 的
`barWidth` 默认值说明写的是 76/80。**每页签恒定差 4vp，两档都差。**

按「哪个是编译产物的一手来源」这条既有判据，**组件的默认行为取正文 76/80**
（`ohos_tabs_width.dart:60-66` 现在就是这么写的，不改），设计稿那套留给调用方
用 `OhosTabsBarWidthRange` 覆盖。但注释里要写明存在两套值，否则下次一定有人
按图改代码。

### 发现 4：5 个页签的 360vp 复现不出来，疑似图注与数值错配

`bottomtab_19` / `_28` 都标「5 个 Tabs → 最大宽度 360vp」。但：

- `80×5+8 = 408`，不是 360；
- `88×5+8 = 448`，也不是 360；
- 而 `88×4+8 = 360` —— **恰好是 ≥600 档 4 个页签的值**。

图内 2/3/4 个页签都能用 `80n+8` 严格复现（168/248/328），只有「5 个页签」这一格
断裂。所以只有两种可能：要么 5 个页签另有封顶（官方正文里没有任何地方提到 360），
要么那张图的数值是从「≥600 档 4 页签」复制过来没改。**在拿到新证据前，不按 360 改实现。**

### 发现 5：MiniBar = TabsBar − 64vp，且上一轮的 264/296 标反了

`bottomtab_28` 逐格比对：4 个 Tabs 时滑动前 328、滑动后 264；5 个 Tabs 时
滑动前 360、滑动后 296。两组差值都是 **64**（收起成圆形按钮后让出的宽度）。
上一轮把 264 记成「5 个 Tabs」、296 记成「4 个 Tabs」，**标反了**，已在
`doc/ux-specs/bottomtab.md` 更正。这类错很危险：数字都对、对应关系错了，
后面谁引都会跟着错。

### 发现 6：`list_20` 的第 4 档，正文 72vp 在图上没有对应行

正文第 95 行：「效率型列表在默认参数下通用高度为 48vp、56vp、64vp、**72vp** 和 96vp」。
图为五行：48 / 56 / 64 / **64** / 96 —— 第 3、4 行都是 64（无图标双行 / 带图标双行）。

所以这不是「图写 64、正文写 72」的数值冲突，而是**图不是正文五档的 1:1 图示**：
五档里的 72 在图上一行都没有。把 64 判成「错」会得出「把第 4 档改成 72」的
错误动作，而实际该做的是「五档里还有一档没被图示」。

### 发现 7：`datapanel` 的 48vp 与栅格体系不同源

设计文档写「横屏左右布局时，左右分别减去 48vp 边距」，而全库栅格边距是
16 / 24 / 32（`ohos_geometry.dart:67-69`，手机 / 折叠 / 平板）。48 不在这个序列里，
也没有独立令牌。做响应式时**不能直接套 `gridMarginLarge = 32`** 冒充它。

### 发现 8：列表侧滑操作区在令牌层完全空白

`list_08 / _10 / _19` 共 17 条值，全部没有令牌。这不是「漏查」：`float.json`
里 `swipe` / `action` / `hotzone` 一类键名一个都没有（只有 `switch_hotzone_*`、
`checkbox_hotzone_padding` 这些无关的）。也就是说列表侧滑的几何规格**只存在于
设计稿**，将来要做必须从图里量，且要自己立常量。

P1 是本轮唯一「规格明确、证据闭合、实现明显没做」的一条，已按建议单独落地，

### 一条方法论：断言里别引用被改的那个常量

P1 的第一版用例写成 `expect(resolveDetent(...), 800 - OhosSheetSpec.topGap)`。
做变异验证时把 `topGap` 改成 `0`，**用例全绿** —— 断言跟着常量一起变了。
改成字面值 `792 / 768` 并与 `expect(topGap, 8)` 分开后，同一次变异 5 条全红。

这类「自指断言」在「常量 + 纯函数」的结构里特别容易写出来：看起来在验公式，
实际在验「公式等于它自己」。凡是 `expect(f(x), g(CONST))` 且 `g` 里含 `CONST` 的
写法，都要先问一句「把 `CONST` 改坏，这条会红吗」。
